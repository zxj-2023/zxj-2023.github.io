my-pi-agent--agent类与hook系统

发表于 2026-07-31 更新于 2026-08-06 分类于 agent实战 ， my-pi-agent 阅读次数：

生命周期事件

事件集对齐 pi 的生命周期模型（Agent/Turn/Message/Tool 四组，正常执行 start/end 成对；被拦截/畸形参数的调用不发射 End）。 每个事件自动带 timestamp（Unix 秒，实例化时刻）。

事件的作用

一、事件的作用：把「可观察」变成「可扩展」

一句话：事件机制让 Agent.run() 成为一个「可被插桩的黑盒」——循环本身写死了，但循环的每一步都广播出去，让任何新功能都能「监听而不改框架」。

先看现在 run() 里实际发生了什么：

这 8 个事件（同步阶段）就是「循环的完整心电图」——每一段代码执行都对应一个事件。而事件的作用 = 把「这段代码发生了」告诉任何想知道的人。

二、核心：为什么事件 = 扩展点

关键洞察在于——你的所有后续功能，几乎都是「想观察循环在干什么」，而不是「想改循环本身」。事件机制让这些功能都变成「加一个 hook」，而不是「改 run()」。

看三个后续阶段怎么用：

扩展 1：session 落盘（阶段 3）—— Agent 显式双写（不是 hook 消费事件流）

（注：早期设计设想过”用 hook 消费事件流写 session”，但实际实现是 Agent 双写——session 是核心功能，显式调用比 hook 更直接、不依赖事件顺序。）

扩展 2：context 压缩（阶段 4）—— prepare 每轮调用（不是监听事件）

ContextCompacted 事件早在设计时就预留了（阶段 4 用）——这就是「事件先定义、后发射」的意义：接口提前定好，实现到时接上。

扩展 3：coding agent UI（未来）—— 渲染过程

hook系统

2026-08-16 重构：hook 从「运行时 register_hook 公共方法」改成「构造参数 hooks=[(事件类, 回调), ...] + HookRegistry 类（对标 ToolRegistry）」。注册表机制（下面讲的 register/emit 逻辑）不变，只是收进了 HookRegistry 类（events.py），Agent 只持有 self.hooks 并在构造时批量注册——和工具一样「构造时批量装配、不对外暴露运行时注册」。

多 hook 注册表

「多 hook 注册表」的机制（仿 CC/Claude Code）。

核心就两个函数：注册（往里放）和触发（到点调用）。

注册：把 hook 挂到事件类名下

  • event_cls = 事件类（如 ToolExecutionStart）
  • callback = 你的函数（(event) -> HookResult | None）
  • 一个事件类可以挂多个回调，按注册顺序存列表

触发：到点时逐个调用

  • 到点 = Agent 循环里 self._emit(ToolExecutionStart(...)) 的位置
  • 逐个调用该事件类型名下所有回调
  • 短路约定：某个回调返回非 None → 立即返回（拦截），不再调后面的

HookResult 干预

hook 回调返回 None = 纯观察；返回 HookResult = 干预。

只有 ToolExecutionStart/End 继承 Interceptable（可被 hook 干预），其余事件纯观察（返回值忽略）。

用起来的样子

机制一句话：注册表 = 事件类 → 回调列表；触发 = 到点时按序调用，短路返回。 你说「在某个事件时调用注册的 hook」——完全正确，_emit 就是那个「到点」的调用点。

设计要点

  1. 单层大脑：状态（messages）+ 循环（run）+ 工具调度全在一个类（pig-mono 式）
  2. 一切可注入、可观察：llm 注入（测试塞 FakeLLM 离线跑）；hook 注册表让外部观察/干预循环
  3. 工具路径永不抛：所有错误（坏 JSON/未知工具/校验失败/工具异常/hook 拦截）转成文本喂回模型，保证「每个 tool_calls 都配上 tool 消息」
  4. hook 异常语义分裂：工具路径 hook 异常转错误字符串（保住配对不变式）；观察路径 hook 异常向上抛（视为使用方 bug）
  5. event 是通知，hook 是干预：纯观察事件（AgentStart/TurnStart/Message*）hook 返回值忽略；ToolExecutionStart/End 可被 HookResult 干预
